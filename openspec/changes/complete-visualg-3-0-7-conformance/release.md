# Version 0.1.0 release handoff

This is the post-merge operations checklist for `complete-visualg-3-0-7-conformance`. It is separate from the implementation checkboxes in `tasks.md`; creating the archive or tag is never a prerequisite for implementation acceptance. This document plans future release work and does not record it as completed.

1. After the complete implementation stack is reviewed and merged, select a clean release-candidate checkout. Verify every checkbox in `tasks.md`, including the final reporting and PR handoff, is complete and backed by evidence. Planning-artifact status from `openspec status` alone is insufficient. Confirm the release tag does not already exist; do not replace an existing tag.
2. Run the release gate on that candidate: strict OpenSpec validation, evidence and implementation-acceptance validation, replay of every required probe and accepted example, and the build/format/vet/lint/test/race/platform/fuzz checks. Require zero pending implementations, mismatches, stale links, unpositioned failures, or missing quality results. Record the candidate commit and evidence hashes. This gate checks implementation tasks, not completion of this operations checklist.
3. Archive the completed OpenSpec change. Resolve its new archive directory and the promoted main specs, then rerun strict validation and traceability validation against those paths. The manifest validator must resolve stable requirement/task IDs in the archive, without continuing to require the former active-change paths. Commit and push the archive and any path-resolution updates only after these checks pass.
4. Recheck release acceptance on the archive commit that will be tagged, including all required quality results for that commit. Confirm that the recorded evidence corresponds to it. Create and push the annotated `v0.1.0` tag pointing to this validated commit. Tag existence is a postcondition of this step, not an input to step 2 or step 3.
5. Record the published tag, target commit, archive location, and validation evidence in the release handoff record. Do not move the tag to include bookkeeping added after publication. Mark an operation performed only after its result is verified.

If any gate fails, retain the failing evidence and repair the cause before continuing with dependent operations. An unavailable Windows/platform result, pending probe, resource-limit hit in an accepted example, or watchdog timeout is not a passing result.
